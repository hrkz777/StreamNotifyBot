# StreamNotifyBot 要件定義書

## 1. 文書の目的

本書は、`やりたいこと.md` に記載された構想を、実装と受け入れ確認に利用できる要件として整理するものです。

元の構想だけでは判断できない事項は「未決事項」、実現方法の提案は「設計案」として区別します。本書の記載によって、未決事項が自動的に確定したものとは扱いません。

## 2. システムの目的

StreamNotifyBot は、複数の配信プラットフォームから配信予定と配信状態を収集し、指定された Discord チャンネルへ通知するシステムです。

次の運用を一元化します。

- 配信者と配信プラットフォーム上のアカウントの登録
- 配信プラットフォームへの Webhook 登録と更新
- Webhook と定期ポーリングを組み合わせた配信状態の追跡
- Discord Webhook を利用した配信通知
- 管理画面による設定
- CSV によるデータの移行とバックアップ

## 3. 前提条件

- アプリケーションは PHP 8.5.9 で実装する
- データベースは MariaDB 10.5 を使用する
- 無料レンタルサーバーなど、常駐プロセスを利用できない環境でも動作可能な構成を目指す
- Dockerfile を用意し、Docker 環境でも実行可能にする
- Discord への送信には Discord Webhook を使用する
- 配信情報の取得方式は、プラットフォームごとに Webhook と API ポーリングを組み合わせる
- 初期対応プラットフォームは YouTube、Twitch、TwitCasting とする

## 4. 利用者と外部システム

| 区分 | 役割 |
| --- | --- |
| 管理者 | 管理画面から通知先、配信者、ポーリング設定などを管理する |
| スケジューラー | Webhook の更新、配信情報のポーリング、通知削除などの定期処理を起動する |
| 配信プラットフォーム | Webhook イベントと配信情報 API を提供する |
| Discord | Webhook 経由で通知を受信し、投稿を保持する |

一般利用者向けのログイン機能や閲覧画面は、現時点の対象に含めません。

| --- | --- |

| ADM-002 | 管理画面は認証されていない利用者からアクセスできないこと |
| ADM-003 | 管理者は通知設定と通知種別ごとの Discord Webhook URL を登録、参照、変更できること |
| ADM-004 | 管理者は配信者を登録、参照、変更できること |
| ADM-005 | 管理者はプラットフォーム単位のポーリング間隔を設定できること |
| ADM-006 | 管理者はジョブ種別ごとの処理件数、最大実行時間、最大再試行回数、バックオフ、リース時間を設定できること |
| ADM-007 | 管理者はプラットフォームごとの API 利用予算、予約枠、警告しきい値を設定し、推定使用量を確認できること |
| ADM-008 | 管理者は初回同期の取得件数、遡及範囲、ページサイズをプラットフォームごとに設定できること |
| ADM-009 | 設定値の保存前に値の整合性を検証し、サーバー停止や API 利用予算超過の危険がある値には警告を表示すること |

認証方式、管理者の追加・削除、パスワード回復、監査ログの要否は未決事項です。

### 5.2 通知設定

| ID | 要件 |
| --- | --- |
| CHN-001 | 1 つの論理的な通知設定を表示名で管理できること |
| CHN-002 | 通知設定ごとに、動画投稿、配信開始前、配信中、配信終了の4種類の通知先を独立して設定できること |
| CHN-003 | 通知設定の各通知種別に、複数の Discord Webhook URL を登録できること |
| CHN-004 | Webhook URL を空にすることで、その送信先への通知を無効にできること |
| CHN-005 | 登録済み Webhook URL を新しい URL に置き換え、他の通知設定へ影響を与えずローテーションできること |
| CHN-006 | 無効な Webhook URL が存在しても、他の有効な送信先への通知を継続できること |
| CHN-007 | 1人の配信者に複数の通知設定を関連付けられること |
| CHN-008 | 通知時は、対象となる通知種別に設定された空ではないすべての Webhook URL へ送信すること |

### 5.3 配信者とプラットフォームアカウント

| ID | 要件 |
| --- | --- |
| STR-001 | 配信者の表示名、英語名、所属区分、表示色を管理できること |
| STR-002 | 1 人の配信者に複数プラットフォームのアカウントを関連付けられること |
| STR-003 | 管理者はハンドルや Screen ID など、取得しやすい識別子を入力してアカウントを登録できること |
| STR-004 | 登録時にプラットフォーム API を呼び出し、入力された識別子を安定したプラットフォーム ID へ解決すること |
| STR-005 | 識別子を解決できない場合、登録を確定せず理由を表示すること |
| STR-006 | 配信者の表示色は、有効なカラーコードだけを受け付けること |

### 5.4 Webhook 購読

| ID | 要件 |
| --- | --- |
| SUB-001 | プラットフォームアカウントの新規登録時、対応プラットフォームが提供する Webhook を購読すること |
| SUB-002 | Webhook 購読に有効期限がある場合、期限切れ前に定期処理で更新すること |
| SUB-003 | 購読状態、有効期限、直近の成功または失敗を確認できること |
| SUB-004 | プラットフォームからの Webhook 検証要求に応答できること |
| SUB-005 | 対応方式が提供されている場合、受信イベントの送信元と完全性を検証すること |
| SUB-006 | 同じイベントが複数回届いても、配信や通知を重複登録しないこと |

### 5.5 配信情報の取得

| ID | 要件 |
| --- | --- |
| POL-001 | Webhook で検知した配信を登録し、API ポーリングの対象にできること |
| POL-002 | 動画投稿、待機所、配信開始、配信終了、およびBOTが表示する情報の変更を識別できること |
| POL-003 | プラットフォーム単位で設定された間隔に従ってポーリングすること |
| POL-004 | 配信状態に応じてポーリング頻度を変更できること |
| POL-005 | 配信終了後も 1 週間は低頻度で配信情報を更新すること |
| POL-006 | 外部 API のレート制限と一時障害を考慮し、他の対象へ影響を広げないこと |
| POL-007 | Webhook とポーリングから同じ更新を取得しても、状態を一貫して処理すること |
| POL-008 | Webhook は変更の迅速な検知に使用し、Webhook 受信後に API から取得した最新情報に基づいて状態と通知内容を確定すること |
| POL-009 | API 取得に失敗した場合は不完全な情報で通知せず、上限付きで再試行すること |
| POL-010 | Webhook の欠落、遅延、順序逆転を定期ポーリングで補完すること |
| POL-011 | 古い Webhook を後から受信しても、保存済みの配信状態を過去の状態へ戻さないこと |
| POL-012 | プラットフォームが提供しないイベント種別は、共通機能へ無理に変換せず非対応として扱うこと |
| POL-013 | プラットフォームごとに設定した API 利用予算と予約枠を考慮し、予算超過が見込まれる処理を延期できること |
| POL-014 | API 利用量はアプリケーションが把握できる呼び出しと操作別コストから推定し、外部で消費された利用量と一致しない可能性を管理画面に表示すること |
| POL-015 | API 利用予算が不足する場合は、初回同期や低頻度追跡より、配信開始前と配信中の状態取得を優先できること |

初期対応プラットフォームの取得分担は次のとおりとします。

| プラットフォーム | Webhook の担当 | API ポーリングの担当 | 初期対象外 |
| --- | --- | --- | --- |
| YouTube | WebSub による動画・待機所の発見とタイトル・説明変更の検知 | 動画種別、予定時刻、開始、終了、タイトル、サムネイルなどの最新状態取得と欠落補完 | なし |
| Twitch | EventSub の `stream.online`、`stream.offline`、`channel.update` による変更検知 | 配信予定、配信状態、タイトル、サムネイルなどの最新状態取得と欠落補完 | 動画投稿通知 |
| TwitCasting | `livestart`、`liveend`、`liveschedulecreate`、`livescheduleupdate`、`livescheduledelete` による変更検知 | 現在の配信、配信予定、タイトル、サムネイルなどの最新状態取得と欠落補完 | 動画投稿通知 |

### 5.6 Discord 通知

| ID | 要件 |
| --- | --- |
| NTF-001 | 動画投稿を検知したとき、「動画投稿」の通知種別へ通知すること |
| NTF-002 | 配信開始30分より前に待機所を初めて検知したとき、「配信開始前」の通知種別へ待機所作成を通知すること |
| NTF-003 | 配信開始まで30分以内かつ開始予定時刻より前に待機所を初めて検知したとき、待機所作成を別途通知せず、「配信開始前」の通知種別へ配信開始30分前として通知すること |
| NTF-004 | 配信開始予定時刻以降かつ配信開始前に待機所を初めて検知したとき、待機所作成と配信開始30分前を別途通知せず、「配信開始前」の通知種別へ配信開始予定時間として通知すること |
| NTF-005 | 配信開始30分より前から追跡している待機所が開始30分前に達したとき、「配信開始前」の通知種別へ通知すること |
| NTF-006 | 追跡中の待機所が配信開始予定時刻に達したとき、「配信開始前」の通知種別へ通知すること |
| NTF-007 | 配信開始を検知したとき、「配信中」の通知種別へ通知すること |
| NTF-008 | 配信終了を検知したとき、「配信終了」の通知種別へ通知すること |
| NTF-009 | タイトル、開始時刻、サムネイルなどBOTが表示する情報の変更を検知したとき、配信終了後を除き、変更時点の状態に対応する通知種別へ通知すること |
| NTF-010 | 新しい通知を行う前に、その配信に対して現在有効な既存の通知投稿をすべて削除し、削除完了後に新規投稿すること |
| NTF-011 | 遷移先の通知種別に有効な Webhook URL がない場合も既存投稿を削除し、新しい通知は投稿しないこと |
| NTF-012 | 対象の通知種別に複数の有効な Webhook URL がある場合、そのすべてへ通知すること |
| NTF-013 | 同じ通知タイミングまたは同じ情報変更に対する通知を重複して投稿しないこと |
| NTF-014 | 配信終了から1週間が経過したとき、その配信に対応する通知投稿を削除すること |
| NTF-015 | Discord への削除または送信が失敗した場合、失敗内容と再試行可能性を記録すること |
| NTF-016 | 配信終了後にタイトルやサムネイルなどBOTが表示する情報が変更されても再通知しないこと |
| NTF-017 | Webhook の表示名とアイコンには、配信プラットフォーム上の配信者名とアイコンを使用すること |
| NTF-018 | Embed に配信者名とアイコン、配信者ページへのリンク、動画または配信のタイトル、コンテンツへのリンク、通知内容、日時、画像、色、通知作成日時を表示すること |
| NTF-019 | 日時フィールドは通知タイミングに応じて「投稿時刻」「予定時刻」「開始時刻」「終了時刻」を使用し、Discord の絶対時刻と相対時刻を併記すること |
| NTF-020 | 配信予定時刻またはタイトルの変更時は変更内容を通知文へ追記し、サムネイルの変更時は Embed 画像へ反映すること |
| NTF-021 | Embed の色は配信者の表示色を優先し、未設定時は YouTube と Twitch を赤、TwitCasting を緑とすること |
| NTF-022 | 動画または配信を X へ共有するリンクボタンを通知へ付けること |

### 5.7 CSV インポート・エクスポート

| ID | 要件 |
| --- | --- |
| CSV-001 | 管理対象のテーブルごとに CSV をエクスポートできること |
| CSV-002 | 管理対象のテーブルごとに CSV をインポートできること |
| CSV-003 | インポート前に形式と参照整合性を検証し、不正行と理由を表示すること |

## 6. 非機能要件

### 6.1 セキュリティ

- 管理画面の全機能を認証および認可の対象とする
- Discord Webhook URL、API キー、アクセストークン、認証情報を秘密情報として扱う
- 秘密情報をログ、画面、CSV、例外メッセージへ平文で出力しない
- SQL インジェクション、XSS、CSRF、SSRF、CSV インジェクションを考慮する
- Webhook 受信では、プラットフォームが提供する署名検証や検証トークンを利用する
- Docker イメージへ秘密情報を含めず、実行時設定として注入する

### 6.2 信頼性

- Webhook の重複配信、順序逆転、遅延を前提に冪等に処理する
- 外部 API と Discord の一時障害には、上限付きの再試行とバックオフを使用する
- 1 件の失敗によって、無関係な配信者や通知先の処理を停止させない
- 定期処理を再実行しても二重通知や不整合を起こさない

### 6.3 可搬性と運用性

- PHP が動作する一般的な Web ホスティング環境を想定する
- 常駐ワーカーを必須とせず、Cron 等から起動できる定期処理を提供する
- Dockerfile から再現可能な実行環境を構築できるようにする
- 環境固有の値は設定として分離する
- 障害調査に必要な処理結果を、秘密情報を除外した構造化ログとして記録する

### 6.4 保守性とテスト容易性

- プラットフォーム固有処理を共通処理から分離する
- HTTP 通信、時計、永続化、Discord 送信をテストで置き換え可能にする
- 状態遷移、重複イベント、期限境界、外部 API エラーを自動テストの対象とする

## 7. 業務ルール

| ID | ルール |
| --- | --- |
| BR-001 | 配信者と各プラットフォームアカウントは分離して管理する |
| BR-002 | プラットフォームの安定 ID を主な照合キーとし、変更可能なハンドルは登録補助情報として扱う |
| BR-003 | 配信終了後 1 週間は低頻度の監視対象とする |
| BR-004 | 配信終了後 1 週間が経過した通知投稿は削除対象とする |
| BR-005 | Discord Webhook URL は個別に有効化、無効化、交換できるものとする |
| BR-006 | 外部イベントと定期処理は、同じ状態変更に対して冪等でなければならない |
| BR-007 | 通知種別は、動画投稿、配信開始前、配信中、配信終了の4種類とする |
| BR-008 | 1人の配信者には複数の通知設定を関連付けられるものとする |
| BR-009 | 初回検知時は現在時刻と配信状態に該当する最も進んだ通知を1回だけ送信する |
| BR-010 | 通知タイミングまたは表示情報の変更ごとに、既存投稿を削除してから新規投稿する |
| BR-011 | 配信終了後の表示情報変更は通知しない |
| BR-012 | 対応プラットフォーム一覧はコードで固定し、追加時は Platform Adapter の実装とアプリケーションのデプロイを必要とする |
| BR-013 | 配信者は必ず所属区分へ関連付け、事務所に所属しない配信者は「個人勢」区分として管理する |
| BR-014 | 定期処理と再試行はレンタルサーバーの Cron から PHP CLI コマンドを起動して実行し、専用キューや常駐ワーカーを必須としない |
| BR-015 | Webhook を変更検知、API を最新状態の取得、定期ポーリングを Webhook 欠落の補完として使用する |
| BR-016 | サーバー性能、Cron 制約、API 利用予算に依存する運用値は固定せず、管理画面から安全な範囲で変更可能にする |

「1 週間」の起点、厳密な日数または時間数、終了時刻が後から訂正された場合の扱いは未決事項です。

## 10. 初期受け入れ条件

- 管理者が4種類の通知種別と種別ごとに複数の Discord Webhook URL を持つ通知設定、配信者、プラットフォームアカウントを登録できる
- 1人の配信者へ複数の通知設定を関連付けられる
- 人が入力しやすいプラットフォーム識別子から安定 ID を取得して保存できる
- Webhook で新規配信を検知し、ポーリングによって動画投稿、待機所、30分前、開始予定時間、開始、終了、表示情報変更を追跡できる
- 各通知タイミングで既存投稿を削除し、通知種別に設定されたすべての有効な送信先へ新規投稿できる
- 通知種別のURLが空の場合は、既存投稿を削除したうえで新規投稿しない
- 状態別の文言、日時、リンク、画像、色を持つ Discord Embed と X 共有ボタンを表示できる
- 配信終了後の低頻度ポーリングと、1 週間後の通知削除を実行できる
- Webhook 購読に期限がある場合、期限切れ前に更新できる
- 管理対象データを安全に CSV で入出力できる
- レンタルサーバー相当の PHP 環境と Docker 環境の双方で実行手順を再現できる
- 主要な正常系、重複イベント、外部サービス障害、期限境界が自動テストで確認されている
